passes (backend app, ETL pipeline, frontend, infra/CI-CD/security) plus an independent

## High

### H1 — Reference-data loaders report `success` while loading nothing
`backend/etl/noaa_weather.py:159-162,213-218`, `backend/etl/dmv_vehicles.py:223-226,265-267`,
`backend/etl/bls_unemployment.py:81-84,164-167`, `backend/etl/load_demographics.py:211-215`

A missing `NOAA_API_TOKEN` logs an error and returns → exit 0 → both `run_job` and
`@track_etl_run` record **success**. Per-county NOAA failures, DMV crosswalk download failure,
BLS quota exhaustion (`status != REQUEST_SUCCEEDED` → `{}`), and demographics failed-years all
follow the same swallow-and-succeed pattern. The loud-failure discipline was applied to FARS
(`nhtsa_fars.py:166-172` raises on `failed_years`) and parties/victims but not these four.

**Failure mode:** token rotates or upstream breaks → every run stays green, freshness stays
green (see M8), weather/unemployment/vehicle data fossilizes with no alert — the exact
"silently green" class the last audit named as its top theme.
**Fix:** track `had_failure` and exit non-zero; `sys.exit(1)` on missing credentials
(as `load_demographics.py:166-167` already does); treat 0 rows where >0 expected as error.

### H2 — Weather and unemployment ingest pinned to end-year 2025; 2026 data never loads
`backend/etl/noaa_weather.py:45`, `backend/etl/bls_unemployment.py:40`, `backend/etl/jobs.py:64-72,136-144`

`DEFAULT_END_YEAR = 2025` and the job registry passes no args, so the monthly jobs re-fetch
2001–2025 forever. It is July 2026: correlation features join 2026 crashes against data that
structurally ends in 2025, and every run is green. This is the same bug the crash loader fixed
(auto-advancing end year) — unfixed in its siblings.
**Fix:** `DEFAULT_END_YEAR = datetime.now().year` (both APIs tolerate partial years), or warn
loudly at startup when `end_year < current_year`. Also check `load_demographics.py:40` (2022)
and `census_tract_density.py:36` (2023) against current ACS availability.

### H3 — All production traffic shares one rate-limit bucket (tunnel IP)
`backend/app/main.py:130` + every router (`ask.py:39`, `admin.py:17`, `crash_people.py:35`…),
`backend/Dockerfile:28` (no `--forwarded-allow-ips`), `docker-compose.prod.yml:29-45`

Independently confirmed by two audit passes. All public traffic ingresses via the `cloudflared`
container, so `request.client.host` — the key for every limiter — is the tunnel's Docker-network
IP for every request; `X-Forwarded-For`/`CF-Connecting-IP` are ignored (gunicorn's default only
trusts 127.0.0.1). Grep confirms zero forwarded-IP handling anywhere in `backend/app/`.

**Failure mode:** `/api/ask` is `10/minute;200/day` — a handful of active users (or one hostile
one) 429s the AI feature for the entire site; the 200/day cap is plausibly exhausted globally
by lunchtime. `/admin/verify` (`5/minute`) can be locked out by anyone. Conversely the
PII-scrape limits on `/parties`/`/victims` no longer bind an individual attacker any tighter
than the whole population.
**Fix:** trust the tunnel as proxy (`FORWARDED_ALLOW_IPS` / `ProxyHeadersMiddleware`) and key
the limiter on `CF-Connecting-IP` validated against Cloudflare ingress; add an integration test
asserting two client IPs get independent buckets; consider a Cloudflare edge rate rule for
`/api/ask`. Note M-B11 (per-worker in-memory limiter state) still quadruples whatever limit you
set.

### H4 — New `/api/crashes/clusters`: unbounded statewide aggregation, no statement timeout
`backend/app/routers/clusters.py:41-129` (verified: `apply_statement_timeout` not imported)

The endpoint the team shipped in feat/280 is missing the exact backstop added everywhere else
one week earlier (`intersections.py`, `stats.py:1150`, `ask.py:48`, guarded by
`tests/test_statement_timeouts.py`). An unfiltered request seq-scans/aggregates the 11M-row
table with a `GROUP BY` on a computed grid expression; `.all()` then materializes every
occupied cell (plausibly 10⁵+ statewide) in the worker. At `1000/minute` with 17 filter params,
cache-busting permutations queue multi-ten-second queries that never die — the same
pool-exhaustion mode commit 67d1e19 called "audit HIGH" for `/ask`.
**Fix:** `apply_statement_timeout(db, 30_000)` as the first statement; add clusters to
`test_heavy_endpoints_call_the_timeout`; consider requiring a county filter or precomputing the
statewide default. Same one-liner needed for `/api/stats/highways` (M11).
(Credit: the feat/280 involvement-flags bug was caught and fixed pre-merge in 26b3943.)

### H5 — Deploy creates the backup bind-mount root-owned; the non-root pipeline container likely can't write backups
`.github/workflows/deploy.yml:185-189`, `docker-compose.pipeline.yml:26-28,45-51`, `backend/Dockerfile:23-24`

`mkdir -p /opt/calsight/backups` runs as the runner user or root (0755); the pipeline container
runs as `USER app` and writes `pg_dump` output to that bind mount. Unless an operator manually
`chown`ed the host dir, every scheduled backup fails with EACCES. The failure *is* alerted —
but only if `ALERT_WEBHOOK_URL`/`HEARTBEAT_URL` are set, and both are optional. Same
silent-recovery-gap class as the old C4: zero local recovery points, nothing to upload to R2,
discovered at restore time.
**Fix:** chown to the image's `app` UID (or `chmod 770` + group) in the deploy step; add a
deploy-time smoke test (`docker compose exec pipeline touch /backups/.write-test`). **Verify on
the prod host today** — and finally run the restore drill the last audit demanded (see M9).

### H6 — Frontend production deploy (Cloudflare Pages) is entirely ungated by CI
`.github/workflows/ci.yml:60-75` (gating job runs eslint/tsc/vitest only; the only
`npm run build` lives in the `continue-on-error: true` Lighthouse job at :125-146)

C3 was fixed for the backend only. Pages builds and publishes the frontend directly on push to
main, in parallel with and regardless of CI. A change that passes tsc/eslint/vitest but breaks
the vite production build (PWA plugin, CSP-hash generation, rollup config, asset import) either
ships broken or fails silently in the Pages dashboard while CI stays green and the backend
deploys. `workers/og-image` has no deploy pipeline at all (manual `wrangler deploy`, no audit
trail).
**Fix:** add `npm run build` to the gating `frontend` job (~1 min); ideally deploy Pages via a
gated workflow (`cloudflare/wrangler-action` after CI) instead of dashboard auto-build; same
for og-image.

### H7 — Global 24-hour `gcTime` retains every heavy heatmap batch in memory (C5's failure mode, via the cache)
`frontend/src/lib/queryClient.ts:56-58`; `frontend/src/hooks/useCrashHeatmap.ts:97-126` (no
per-query override); persistence whitelist `frontend/src/lib/queryPersistence.ts:26-35`

The default `gcTime` was raised to 24h to match offline-persistence maxAge — but the
persistence whitelist explicitly *excludes* `crashHeatmap`, so the heaviest queries gain
nothing from the long lifetime and pay all its cost: every county-detail batch (up to 150k
points × 15 fields) and every statewide raw response is retained in memory for 24h after
unmount, keyed per filter permutation. The live accumulator is capped at 600k (C5 fix); the
cache underneath is not.
**Failure mode:** mobile user opens LA county detail (~600k points cached), toggles severity,
a date range, two more counties — each permutation caches full batch sets, nothing is collected
during the session → hundreds of MB of resident objects → the same mobile tab kill C5 was
about, now invisible because the on-screen point count looks bounded.
**Fix:** short explicit `gcTime` (5–10 min) on `crashHeatmap`/`crashClusters` queries — or
invert: keep a 5-min global default and set 24h only on the whitelisted persisted roots.

## Medium

### Deploy path & infra

**M1 — deploy and run-etl use disjoint concurrency groups despite claiming mutual exclusion.**
`run-etl.yml:24-29` (`group: run-etl`) vs `deploy.yml:13-14` (`group: production-deploy`). A
deploy's `up -d` recreates the backend container mid-ETL-exec, killing the job mid-write and
stranding a zombie `running` row; or the deploy's backfill races the manual job on the same
tables. Fix: one shared group (`prod-mutex`, `cancel-in-progress: false`).

**M2 — Rollback restores the old image against the already-migrated schema, never rolls back the
pipeline container, and waits only 5s.** `deploy.yml:183` (migrations run before health
verification), `:257-276` (rollback touches only `backend`; pipeline image is never SHA-tagged;
single probe after `sleep 5` under-measures a gunicorn cold start). Fix: SHA-tag and include
pipeline in rollback; reuse the 6×5s retry loop; document expand/contract migration policy.

**M3 — Re-running an old green CI run silently redeploys that old commit.** `deploy.yml:8-11`
(`workflow_run` fires on re-runs) + `:28` (deploys that run's `head_sha`). An innocent "re-run
to check flakiness" on a months-old CI run rolls production back to that SHA, including
`alembic upgrade head` from old code. Fix: verify the SHA is current main head (or
`run_attempt == 1`).

**M4 — check-backfill diffs only `HEAD~1`; multi-commit direct pushes skip required backfills.**
`deploy.yml:49,61-67`. Migrations still apply but `backfill_derived`/matview refresh are
skipped → NULL derived columns served silently. Fix: diff against the previously-deployed SHA.

**M5 — Team DB credentials distributed via Discord.** `backend/app/settings.py:28-30`,
`backend/.env.example:4-7`. Chat-posted shared credentials live forever in Discord
history/exports; combined with H-S2 (dev Postgres on 0.0.0.0) the blast radius is large. Fix:
per-developer roles + rotation; remove the instruction from committed code.

### ETL & data integrity

**M6 — Validation outcomes are recorded but consumed by nothing.** `orchestrator.py:239-242`
writes `validation_status`; no consumer in `pipeline.py`/`alerts.py`/`pipeline_health.py`. A
>5% crashes row-drop validation failure produces the *"All jobs completed successfully"* alert.
Fix: WARNING/ERROR alert when any result has `validation_status == "failed"`.

**M7 — Process-lifetime CKAN discovery cache in the long-lived scheduler partially reintroduces
the January no-op.** `ckan_api.py:60-101` caches discovery per process; the freshness probe
runs inside the weeks-old scheduler process (`_utils.py:351-363`, `orchestrator.py:169-176`).
When CHP publishes `Crashes_2027`, the daily job skips as `skipped_unchanged` until the weekly
force run (fresh subprocess) picks it up — 2027 data at weekly not daily cadence, freshness
green throughout. Fix: TTL the cache (6–24h) or key per pipeline run.

**M8 — "Federal" freshness is self-referential and can deadlock a source into permanent skips.**
`_utils.py:448-473` compares the target table's own row count to the last success. A run that
adds no rows (upstream unchanged, silently failing per H1, or year-pinned per H2) freezes the
count → `is_fresh=False` forever → job never runs daily again; `/api/freshness` counts skips as
syncs (`freshness.py:35`) so `is_stale` never trips. Related: **an ArcGIS endpoint outage reads
as "unchanged" forever** (`_utils.py:426-436`; the pinned `speed_limits` freshness URL is a
2022-vintage service, `jobs.py:116`). Fix: probe the real upstream; distinguish "verified
unchanged" from "could not verify"; alert after N consecutive unverifiable checks.

**M9 — Restore correctness gaps: the documented restore produces a broken API; dumps are never
verified.** `backup.py:256-270` dumps `--no-owner --no-acl`; the documented
`pg_restore --clean` therefore drops all grants to `calsight_api_ro` — the API 403s on every
table until `create_readonly_role.sql` is re-applied, and no runbook step says to. No
`pg_restore --list` integrity check after dump (a truncated dump rotates in as a "good"
recovery point). Docstring falsely claims `etl_runs` is excluded. The restore drill flagged
2026-07-01 has still never been run. Fix: post-dump `pg_restore --list >/dev/null`; grants
re-apply step in the runbook (or drop `--no-acl`); run one real restore.

**M10 — Party-derived crash flags are set-once: stale-FALSE drift on DUI/drug/cyclist/
distraction metrics.** `backfill_derived.py:241-251,303-313,429-441,475-487,505-538` — positive
updates carry `AND <col> IS NULL`; the FALSE pass then locks the value forever. Parties reload
current+prev year daily, so routine CCRS amendments (e.g. toxicology flipping sobriety) are
never reflected → systematic DUI undercount concentrated in the most-viewed recent years.
`backfill_pedestrian_flags` was rewritten to ground-truth `IS DISTINCT FROM` semantics for
exactly this bug class; its four siblings were not. Fix: apply the pedestrian pattern.

**M11 — `/api/stats/highways` missing the statement-timeout backstop.** `stats.py:974-1069`
aggregates millions of rows with the full 17-filter surface at 1000/minute; unlike its peers it
never calls `apply_statement_timeout`. Fix: one line + add to the guard test.

**M12 — `generate_insights` builds county cards from the partial current year and regenerates
58 LLM narratives daily.** `generate_insights.py:94-110` (no current-year exclusion, unlike
`generate_llm_cards.py:296-300`), `:139-153` (`yoy_change_pct` divides partial year by full
prior year → every county reads ≈ −50% in July), `:363-370` (daily count churn defeats the
skip-if-unchanged guard → 58 LLM calls/day). Fix: exclude the current calendar year.

### AI answer correctness

**M13 — Three ways the AI gives confidently wrong or degraded answers:**
- **`pct_of_total` is the share of the top-N rows, not the filtered total**
  (`ai_tools.py:196-200` sums the already-`LIMIT`ed results): "LA accounts for X% of California
  crashes" reads ~2× the true share. Fix: ungrouped-count denominator or `SUM() OVER ()`.
- **`rank_counties`/`get_trend` silently substitute `crash_count` for unrecognized metrics and
  label the result with the requested name** (`ai_tools.py:244-260,277,373-387,400`). The
  repo's own quality script sends off-enum metrics; "worst hit-and-run rate?" gets total crash
  counts labeled `hit_run_pct`. Fix: validate and return an error (pattern already exists at
  `ai_tools.py:949-950`).
- **One failed tool query poisons the whole ask transaction** — `ask.py:283-292` catches the
  exception but never `db.rollback()`, so every later tool call raises `PendingRollbackError`
  masked as "Tool execution failed"; `tools_called` is appended *before* execution (`:282`), so
  `grounded=true` even when every tool errored, and the degraded answer is cached for an hour
  (`ask.py:172`, `llm_cache.py:122`). Same missing rollback in `ai_prompt.py:237-244`
  (Quick Facts). Fix: rollback + re-apply statement timeout in the except branch; set
  `grounded` from successful executions; skip caching degraded answers.

### Frontend & edge

**M14 — og-image worker: `initWasm` race + no edge caching + unauthenticated CPU-heavy render.**
`workers/og-image/src/index.ts:26,266-269` (two concurrent cold-start requests double-init;
`@resvg/resvg-wasm` throws "already initialized" → 500 exactly when a link fans out to multiple
crawlers), `:274-285` (`s-maxage` does not cache Worker-generated responses; the Cache API/KV
binding is commented out, `wrangler.toml:9-13`). Every request with a unique `?title=` is a
full WASM SVG→PNG render — a trivial paid-CPU burn. Confirmed independently by two audit
passes; open since the last audit. Fix: `initPromise ??= initWasm(...)`; read/write
`caches.default` keyed on the normalized URL; clamp params at parse time.

**M15 — Dual-axis charts are silently broken: the secondary measure is never fetched.**
`DashboardGrid.tsx:36-39,205` expects `dataBySlot["${dimension}:${secondaryMeasure}"]`, but
`useDashboardData.ts:209-252` only ever writes primary keys (verified: `secondaryMeasure` does
not appear in the file). User configures "Dual axis: Crashes vs Fatalities" → single-axis chart,
no error. Fix: populate the secondary key in the `dataBySlot` loop + regression test.

**M16 — Persistence whitelist admits the whole `stats` root: multi-MB synchronous
`JSON.stringify` per write and a realistic localStorage-quota path.** `queryPersistence.ts:14-35`
whitelists by root; `stats/batch` payloads are hundreds of KB each and timelapse multiplies
entries (all alive 24h per H7). `createSyncStoragePersister` has no `retry`, so
`QuotaExceededError` silently stops persisting. Fix: exclude `["stats","batch"]` (or gate on
size); pass `retry: removeOldestQuery`.

**M17 — ErrorBoundary "Try again" wipes the entire query cache app-wide.**
`ErrorBoundary.tsx:62` calls `queryClient.clear()`; boundaries wrap individual chart cards
(`DashboardGrid.tsx:201`). One chart hiccup → refetch storm across every page *and* the
persister overwrites the offline snapshot with the emptied cache. Fix: drop the `clear()` or
scope invalidation to the failing subtree.

**M18 — Cluster side panel shows stale hotspot stats.** `MapPage.tsx:100,329-332,577-578` —
`selectedCluster` is a snapshot; filter changes refetch and move/remove markers but the open
panel keeps the old cluster's counts/z-score, and it survives the layer being toggled off. The
equivalent highway staleness was explicitly fixed (`handleSelectedHighwayGone`,
`MapPage.tsx:336-339`). Fix: mirror that pattern.

**M19 — `POST /api/etl/run` is the only endpoint with no rate limit — unthrottled online
brute-force of the ETL API key.** `etl.py:131-150` (`_verify_etl_key` is constant-time but
unlimited; siblings are 5–10/minute). Fix: `@_limiter.limit("5/minute")` (weak until H3 lands,
but consistent).

**M20 — No HSTS header anywhere in-repo.** `frontend/public/_headers:20-26`,
`backend/app/main.py:113-121`. May be set in the Cloudflare dashboard, but nothing in-repo
guarantees it. Fix: add `Strict-Transport-Security` in both (idempotent if edge also sets it).

**L6 — Degraded/simple-mode ask answers cached 1h indistinguishably from good ones.**
